### New EventEffect (chosen approach: ADD a new `'advancement_dm'` type with a `value` field):
```typescript
export interface EventEffect {
  type:
    | 'skill' | 'characteristic' | 'contact' | 'ally' | 'rival'
    | 'enemy' | 'choice' | 'special' | 'benefit' | 'injury'
    | 'advancement_dm';        // NEW
  detail: string;
  options?: string[];
  value?: number;              // NEW — used by advancement_dm, optional for others
}
```
Why this approach: minimizes change surface (no rename or overload), is explicit at the effect-type level, and plays nicely with the Zod schema. Choice-variant events remain encoded as `choice` effects with string options; the advancement_dm effect can appear alongside a `choice` effect if the event grants the DM unconditionally, or as a separate resolution in the parent component when the user picks the "DM+4 advancement" option.

### Data encoding strategy:

**Plain advancement-DM events** (unconditional, no choice): REPLACE the `benefit` effect with an `advancement_dm` effect:
```json
// BEFORE
"effects": [{ "type": "benefit", "detail": "DM+2 to next advancement roll" }]
// AFTER
"effects": [{ "type": "advancement_dm", "detail": "DM+2 to next advancement roll", "value": 2 }]
```

**Choice-variant events** (user picks "DM+4 advancement" or something else): ADD an `advancement_dm` effect ALONGSIDE the choice effect. The CareerEventCard detects the user's choice and only applies the DM if that option was picked. Example from army.json:125:
```json
// BEFORE
"effects": [
  { "type": "skill", "detail": "Gain Tactics (Military) 1" },
  { "type": "choice", "detail": "Gain Ally or DM+4 to next advancement", "options": ["Ally", "DM+4 advancement"] }
]
// AFTER — add advancement_dm with conditional value via option index matching
"effects": [
  { "type": "skill", "detail": "Gain Tactics (Military) 1" },
  { "type": "choice", "detail": "Gain Ally or DM+4 to next advancement", "options": ["Ally", "DM+4 advancement"], "value": 4 }
]
```
Here we put `value: 4` ON the choice effect itself. The CareerEventCard is responsible for checking "did the user pick the option whose text contains 'advancement' AND does this choice have a numeric value?" — if yes, use that value as the advancement_dm bonus. This keeps the JSON schema simple (no conditional option-to-effect mapping) and centralizes the parsing in one place.

**Rule of thumb for data entry:**
- Unconditional DM event → use `{type: 'advancement_dm', detail: '...', value: N}`
- Choice-variant DM event → keep the `choice` effect, add `value: N` to it (where N is the DM on the advancement option)

**Bonus detection logic inside CareerEventCard:**
```typescript
function computeAdvancementBonus(
  effectSource: CareerEvent,
  choiceIndex?: number,
): number {
  let bonus = 0;
  for (const eff of effectSource.effects) {
    if (eff.type === 'advancement_dm' && typeof eff.value === 'number') {
      bonus += eff.value;
    }
    if (eff.type === 'choice' && choiceIndex !== undefined && typeof eff.value === 'number') {
      const option = eff.options?.[choiceIndex];
      // Only apply the DM if the user picked the option containing "advancement" (case-insensitive)
      if (option && /advancement/i.test(option)) {
        bonus += eff.value;
      }
    }
  }
  return bonus;
}
```
Note: life-event redirects (rollValue === 7) never grant advancement DMs — they're Life Events table entries which don't have advancement_dm effects, so this function naturally returns 0 for them.
